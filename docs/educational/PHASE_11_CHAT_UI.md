## 2. WHY Do Server-Sent Events (SSE) Matter for LLMs?

Standard HTTP request/response protocols require the client to wait until the entire text generation finishes before receiving an answer. For an autoregressive language model generating 250 tokens at 20 tokens/second, this would cause a **12.5-second freeze** with no feedback.

### The SSE Streaming Solution:
- **Server-Sent Events (`text/event-stream`)**: A standard HTTP persistent connection where the server pushes chunks of text as soon as each token is generated by the transformer.
- **Immediate TTFT**: The user sees the first token within ~100–300 ms, perceiving the interface as instantaneous while subsequent tokens arrive continuously.
- **Low Overhead**: Unlike WebSockets (which require a dual-direction protocol upgrade and separate connection handling), SSE operates over standard HTTP/1.1 or HTTP/2 GET/POST requests.

## 3. HOW The Wire Protocol Operates

### The Wire Format:
The FastAPI backend formats each token delta according to the SSE standard:
```text
data: {"choices": [{"delta": {"content": "Attention"}}]}

data: {"choices": [{"delta": {"content": " is"}}]}

data: {"choices": [{"delta": {"content": " all"}}]}

data: [DONE]
```

### The Client-Side Stream Reader:
In `apps/frontend/src/lib/api.ts`, we consume the byte stream and parse UTF-8 text line-by-line:
```typescript
const response = await fetch(`${API_BASE_URL}/chat/completions`, {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ ...req, stream: true }),
});

const reader = response.body?.getReader();
const decoder = new TextDecoder('utf-8');

while (true) {
  const { done, value } = await reader.read();
  if (done) break;

  const chunk = decoder.decode(value, { stream: true });
  for (const line of chunk.split('\n')) {
    if (line.startsWith('data: ')) {
      const dataStr = line.replace('data: ', '').trim();
      if (dataStr === '[DONE]') return;
      const json = JSON.parse(dataStr);
      const delta = json.choices?.[0]?.delta?.content;
      if (delta) yield delta;
    }
  }
}
```

## 4. Sampling Hyperparameters Demystified

The UI allows configuring three key parameters:

1. **Temperature ($T$)**:
   - During generation, logits $z_i$ are divided by $T$ before the softmax:
     $$p_i = \frac{e^{z_i / T}}{\sum_j e^{z_j / T}}$$
   - When $T \to 0$, the probability distribution sharpens into argmax (greedy decoding, purely deterministic).
   - When $T \approx 0.7 - 1.0$, the distribution flattens, enabling creative and diverse completions.

2. **Top-p (Nucleus Sampling)**:
   - Instead of sampling from all possible vocabulary tokens, sorts tokens by probability and retains only the top subset whose cumulative probability exceeds $p$ (e.g. 0.9).
   - Truncates the long, improbable tail of vocabulary words, preventing nonsensical outputs.

3. **Max Tokens**:
   - Strict generation ceiling preventing runaway CPU inference loops.
